# 1. 定位系統整體流程

本頁以目前程式為準。作業從 MQTT vision/operation/start 開始，後端建立作業並通知 AI，再回覆包含 requestId 與 backendInstanceId 的 ACK。影像端在收到對應 ACK 後開始。
兩條影像管線要區分：cam-color/cam-depth 的 RTSP 供預覽與錄影，不能單靠兩路 RTSP 到達時間保證同幀。精確定位使用 /ws/rgbd，在一個封包中帶 JPEG 彩色、PNG16 深度、frameId、capture timestamp 與校正參數。
UWB 與 IMU 經 MQTT 進後端。即時只運算選中的人員定位法。4D-GWO 估計位置與共同距離偏差 b，IMU 提供姿態。兩者組成設備 pose，由 AI 的 pose buffer 在影像時間取得相符 pose。
同幀原始世界座標經 Hungarian 關聯，進行螺絲多幀融合，再保存並供前端查詢。同幀螺絲支線目前會保留四種融合結果，與人員定位即時只算選定方法不同。
目前 test_depth.mp4 為灰階換算的示範深度，偵測器預設 mock_yolo。真實相機同步、時鐘校準與 YOLO 權重尚須硬體端交接。
程式依據：AI/test/test2.py、AI/test/rgbd_sender.py、AI/rgbd_api.py、backend/src/mqtt/mqttClient.js、backend/src/positioning/rgbdFusion.js。

# 2. 同幀 RGB-D 接收與品質判斷

邊緣端先把深度對齊彩色影像，再傳同一個二進位 RGB-D 封包。彩色使用 JPEG，原始 uint16 深度使用 PNG16。每個封包包含 operationId、sessionId、clockId、frameId、colorCaptureTimeNs、depthCaptureTimeNs、intrinsics、depthScaleMeters 與 calibrationId。
AI 先檢查格式、尺寸、型別及序列。重複或倒序 frameId、不單調 capture time 拒絕處理。frameId 跳號只累計 missingFrames，不把下一張深度錯配前一張彩色。
兩路擷取時間差門檻為 20 ms。超過時記錄 pair_time_mismatch，不產生有效定位。此數字是工程設定，需真實硬體測試校準。
PoseBuffer 在彩色擷取時間找精確 pose，或以前後 pose 位置線性插值、四元數 SLERP。前後間隔須不超過 200 ms。缺少包夾樣本時不外插最新 pose，WebSocket 接收可先短暫等待右側 pose。200 ms 是 pose 樣本間隔門檻，不等於固定等待 200 ms。
彩色影像經偵測器得到 bbox 和中心座標，同幀深度中心 5×5 有效值中位數取得公尺深度，再做相機內參反投影。無偵測、無效深度、pose 缺少或外參版本不合時保留狀態與影像，不產生有效世界定位觀測。
本機示範 sender 把後端 pose timestamp 寫入影像 metadata，只能驗證軟體流程，尚未證明真實攝影機與 IMU 的硬體時鐘同步。
程式依據：AI/rgbd_sync.py、AI/rgbd_api.py、AI/test/rgbd_sender.py。

# 3. 4D-GWO 設備定位流程

4D 的第四維是共同加性測距偏差 b，不是 yaw。狀態向量 x=[x,y,z,b]^T。各站預測距離為設備與已知基地站的歐氏距離加 b，目標是所有測距殘差平方和最小。
每次至少五個不同基地站的有效正距離，並檢查四維資訊矩陣可逆性。八站位於 20×12 m 場域四角，各有 z=0 與 2.5 m。搜尋高度範圍 0～2.8 m。
使用 100 隻狼、100 次迭代，搜尋範圍均勻初始化，歷史 alpha/beta/delta 領導狼，a=2[1-(t/T)^2]。保留原 MATLAB 的主要更新機制，沒有額外 warm start 或局部精修。
預設 b=0～0.6 m，包含零偏差。可由 GWO4D_BIAS_MIN/MAX 還原 0.1～0.6 m。範圍包含零並不保證精度優於其他方法。
求解成功更新設備位置與 b，IMU 仍沿用既有角速度積分或模擬 heading，GWO 分支不以加速度推進位置。這不是完整 INS 緊耦合，也沒有新增航向漂移校正。求解失敗保留先前狀態，拒絕新的未就緒同幀 pose。
即時只跑當下選定人員定位法。相同原始距離固定隨機種子，讓事後重播可重現。局部資訊矩陣給的是近似方差，不是全域最佳保證。
程式依據：backend/src/positioning/gwo4d.js、esEkf.js、mqtt/mqttClient.js。

# 4. 螺絲定位、關聯與多幀融合

先由偵測 bbox 中心及同幀深度反投影至相機座標 p_C。將相機座標用設定的相機對設備外參 R_C^B、t_C^B 變到設備座標，再用該幀設備世界姿態 R_B^W 和位置 p_B^W 變到世界座標。
公式是 p_s^W=R_B^W(R_C^B p_s^C+t_C^B)+p_B^W。R_B^W 由設備四元數得到。這裡原始世界位置是量測，不能直接拿既知螺絲地圖位置替代它。
Hungarian 在同一幀的多個觀測與地圖螺絲間找一對一配對。目前成本是歐氏距離，先做 0.8 m 門檻與已知類別一致性檢查，加入虛擬欄允許未配對。未配對觀測保留標記，不更新既知螺絲位置。
配對成功後每顆螺絲保留最近 60 筆觀測。平台同幀管線會計算並保存平均法、EKF、ES-EKF、RMV-FGO 四種結果，前端螺絲融合選單決定呈現結果。這與人員演算法即時僅計算選中方法不同。
注意平台 RMV-FGO 是目前 JavaScript 實作，其狀態與參數須依 screwFusion.js 說明，不能直接套用 Python 模擬中設備平移與 yaw 聯合優化版的全部假設。
附近提示目前由設備 pose 與工作場域螺絲資訊判斷，MQTT vision/notification 發文字，並非只在攝影機正前方才提示。
程式依據：AI/rgbd_sync.py、backend/src/positioning/rgbdFusion.js、screwFusion.js、screwWorkspace.js、mqtt/mqttClient.js。

# 5. 資料保存、結束作業與歷史回放

原始 UWB 和 IMU 在串流期間持續存入 RawSensorMeasurement，與是否偵測到螺絲無關。RGB-D 端先寫原始 RGB-D 封包、逐幀 sidecar JSON 與 pending journal，再送後端 frames API。MongoDB 成功寫入並融合後才回 persisted ACK，失敗不假裝成功，pending 可補送。
RgbdFrame 保存 sessionId、frameId、capture/received/processed time、原始封包路徑、devicePose、偵測與融合狀態。彩色與深度可用逐幀媒體回放，同幀頁面不虛構與獨立 RTSP MP4 的時間對應。
正常停止時 test2 停止發送，RGB-D end 刷新 pending，再送 vision/operation/end。AI 也有串流中斷監測，例如 RGB-D 斷訊 10 秒結束作業，首幀等待另有 120 秒門檻。RGB-D 的 ended 回應只代表該會話結束，不能把它當成 MongoDB 作業 endTime 已經寫好。
後端結束作業時寫入 endTime，從原始 UWB/IMU 以 worker 重播四種人員演算法，結果依 fusionAlgorithm 分別存入 OperatorTelemetry。舊紀錄若沒有原始感測資料無法補算。
歷史頁讀取資料庫 snapshot，按影片目前時間限制路徑，勾選哪種演算法就顯示相應設備與軌跡。暫停時影片、bbox、設備與路徑保持相同幀，續播接續。即時暫停只凍結前端，後端持續接收保存，恢復時跳到最新狀態。
程式依據：AI/rgbd_api.py、AI/main.py、backend/src/routes/rgbdRoutes.js、mqtt/mqttClient.js、positioning/telemetryReplayWorker.js、frontend/src/components/RgbdViewer.vue。
